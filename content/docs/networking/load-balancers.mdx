## Resumen

**Elastic Load Balancing (ELB)** distribuye automáticamente el tráfico entrante entre múltiples targets (instancias EC2, contenedores, funciones Lambda, IPs) en una o más Availability Zones, mejorando la disponibilidad y la escalabilidad de las aplicaciones.

AWS ofrece tres tipos de load balancers modernos: **ALB** (capa 7), **NLB** (capa 4) y **GWLB** (capa 3).

## Conceptos Clave

### Tipos de Load Balancer

| Feature | ALB | NLB | GWLB |
|---|---|---|---|
| **Capa OSI** | Capa 7 (HTTP/HTTPS) | Capa 4 (TCP/UDP/TLS) | Capa 3 (paquetes IP) |
| **Caso de uso** | Apps web, microservicios, contenedores | Gaming, tiempo real, IP estática | Appliances de seguridad de terceros |
| **IP estática** | No | Sí | No |
| **Target types** | IP, instancia, Lambda | IP, instancia, ALB | IP, instancia |
| **Protocolo GENEVE** | No | No | Sí (puerto 6081) |
| **Terminación SSL** | Sí | Sí (TLS passthrough opcional) | No |
| **WebSocket** | Sí | Sí | No |
| **Routing basado en contenido** | Sí | No | No |

### Sticky Sessions (Sesiones Pegajosas)

Las Sticky Sessions garantizan que las solicitudes de un mismo cliente se dirijan siempre al mismo target.

| Tipo | Descripción | Duración |
|---|---|---|
| **Duration-based** | Cookie generada por el load balancer (`AWSALB`) | Configurable (1 s a 7 días) |
| **Application-based** | Cookie personalizada generada por la aplicación | Definida por la aplicación |

> **Nota:** Las Sticky Sessions pueden causar distribución desigual de carga. Solo usar cuando la aplicación requiere estado de sesión en el servidor.

### Connection Draining / Deregistration Delay

- Cuando un target se elimina o se marca como no saludable, el load balancer **espera que las conexiones en curso se completen** antes de dejar de enviarle tráfico.
- **Tiempo por defecto:** 300 segundos (5 minutos).
- Rango configurable: 1 a 3,600 segundos. Establecer en 0 para deshabilitar.

### ALB Autenticación

ALB puede autenticar usuarios directamente antes de reenviar la solicitud al backend:

- **Amazon Cognito:** Para autenticación con user pools.
- **OIDC compatible:** Google, Facebook, Apple, cualquier proveedor OIDC.
- El token de autenticación se pasa como header al backend.

### Cross-Zone Load Balancing

| Load Balancer | Estado por defecto | Costo inter-AZ |
|---|---|---|
| **ALB** | Siempre habilitado | Sin costo adicional |
| **NLB** | Deshabilitado por defecto | Se cobra transferencia inter-AZ |
| **GWLB** | Deshabilitado por defecto | Se cobra transferencia inter-AZ |

- **Sin cross-zone:** Cada nodo del LB distribuye solo entre targets en su propia AZ.
- **Con cross-zone:** Cada nodo del LB distribuye equitativamente entre todos los targets en todas las AZs.

### X-Forwarded-For

- Cuando un cliente se conecta a través de un load balancer, el target ve la IP del load balancer, no la del cliente.
- El header **`X-Forwarded-For`** contiene la IP original del cliente.
- **`X-Forwarded-Proto`** contiene el protocolo original (HTTP o HTTPS).
- **`X-Forwarded-Port`** contiene el puerto original.

### GWLB (Gateway Load Balancer)

- Diseñado para desplegar, escalar y administrar **appliances de seguridad de terceros** (IDS/IPS, firewalls, inspección de paquetes).
- Usa el protocolo **GENEVE en el puerto 6081** para encapsular el tráfico.
- Opera en **capa 3**: recibe paquetes IP, los envía al appliance y devuelve el tráfico procesado.
- Patrón típico: tráfico entrante → GWLB → appliance (inspección) → GWLB → destino final.

## Comparativa: ALB vs NLB vs GWLB

| Característica | ALB | NLB | GWLB |
|---|---|---|---|
| **Capa** | 7 | 4 | 3 |
| **Protocolo** | HTTP/HTTPS | TCP/UDP/TLS | IP (GENEVE) |
| **IP estática** | No | Sí | No |
| **Routing por contenido** | Sí | No | No |
| **Lambda como target** | Sí | No | No |
| **ALB como target** | No | Sí | No |
| **Preserva IP cliente** | Header X-Forwarded-For | Sí (IP de origen) | Sí |
| **Casos de uso** | Apps web, APIs, microservicios | Gaming, VoIP, IoT | IDS/IPS, firewalls inline |

## Casos de Uso

| Escenario | Load Balancer recomendado |
|---|---|
| Aplicación web con múltiples rutas (`/api`, `/web`) | ALB con path-based routing |
| Necesito una IP estática para el load balancer | NLB |
| Inspección de paquetes con firewall de tercero | GWLB |
| Terminación TLS en el load balancer | ALB o NLB |
| Enrutar tráfico a funciones Lambda | ALB |
| Gaming con UDP | NLB |
| Autenticación con Cognito antes del backend | ALB |

## ALB: Reglas de Enrutamiento Avanzadas

El ALB soporta reglas de enrutamiento basadas en múltiples condiciones:

| Condición | Ejemplo |
|---|---|
| **Path** | `/api/*` → Target Group API |
| **Host header** | `admin.example.com` → Target Group Admin |
| **HTTP header** | `X-Custom-Header: premium` → Target Group Premium |
| **HTTP method** | `POST` en `/upload` → Target Group Upload |
| **Query string** | `?version=2` → Target Group V2 |
| **Source IP** | `10.0.0.0/8` → Target Group Internal |

Las reglas se evalúan en **orden de prioridad** (número más bajo = mayor prioridad). La última regla siempre es la regla por defecto.

### Acciones en las Reglas

| Acción | Descripción |
|---|---|
| **Forward** | Enviar al target group especificado |
| **Redirect** | Redirigir a otra URL (HTTP→HTTPS, cambio de dominio) |
| **Fixed Response** | Retornar una respuesta estática (200, 403, 503) |
| **Authenticate** | Autenticar con Cognito/OIDC antes de reenviar |

## Health Checks

Todos los tipos de ELB realizan **health checks** para detectar targets no saludables:

| Parámetro | Descripción | Valor típico |
|---|---|---|
| **Protocol** | HTTP, HTTPS o TCP | HTTP |
| **Path** | Ruta del endpoint de health check | `/health` |
| **Healthy threshold** | Checks exitosos para marcar saludable | 3 |
| **Unhealthy threshold** | Checks fallidos para marcar no saludable | 3 |
| **Timeout** | Tiempo de espera por respuesta | 5 s |
| **Interval** | Frecuencia de verificación | 30 s |
| **Success codes** | Códigos HTTP que indican salud | 200-299 |

> Un target se elimina del pool de enrutamiento si supera el **unhealthy threshold**. Se vuelve a agregar automáticamente cuando pasa los health checks.

## Esquemas: Internet-facing vs Internal

| Esquema | Descripción | Casos de Uso |
|---|---|---|
| **Internet-facing** | ELB tiene IP pública, accesible desde internet | Frontend, web apps públicas |
| **Internal** | ELB tiene solo IP privada, solo accesible en VPC | Backend, microservicios internos, capa de DB |

Un patrón común de arquitectura multi-capa:

```
Internet → ALB (internet-facing) → EC2 Web Layer
                                         ↓
                              ALB (internal) → EC2 App Layer
                                                     ↓
                                          RDS / ElastiCache
```

## Configuración

Pasos típicos para crear un ALB:

1. Ir a **EC2 → Load Balancers → Create Load Balancer → Application Load Balancer**.
2. Seleccionar **esquema**: Internet-facing (público) o Internal (privado).
3. Seleccionar **VPC y subnets** (mínimo 2 AZs para alta disponibilidad).
4. Configurar **Security Groups**.
5. Configurar **Listeners** (puerto 80, 443).
6. Crear **Target Groups** y agregar targets (instancias, IPs, Lambda).
7. Definir **Reglas de enrutamiento** en el listener.

<Callout type="warn">
**Exam Tips — SAA-C03:**
- **ALB = capa 7 (HTTP/HTTPS)**, enruta por path, host header, query string, source IP.
- **NLB = capa 4 (TCP/UDP)**, más rápido, soporta IP estática — elegir para gaming o IP fija requerida.
- **GWLB = capa 3**, para appliances de seguridad inline (IDS/IPS/firewalls) usando protocolo GENEVE.
- **X-Forwarded-For** para obtener la IP real del cliente detrás de un ALB.
- **ALB puede enrutar a funciones Lambda** como target.
- **Cross-zone load balancing:** ALB siempre habilitado sin costo; NLB deshabilitado por defecto, tiene costo inter-AZ.
- **Sticky Sessions** pueden causar distribución desigual — solo para aplicaciones stateful.
- **Connection Draining** (300 s por defecto) permite completar solicitudes en vuelo antes del deregistro.
- **NLB preserva la IP de origen** del cliente; ALB usa X-Forwarded-For.
</Callout>
