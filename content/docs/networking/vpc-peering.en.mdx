## Overview

A **VPC Peering** is a private network connection between two VPCs that allows their resources to communicate with each other using **private IP addresses**, as if they were on the same network. Traffic does not traverse the internet, a VPN, or an external gateway — it travels directly through the AWS network infrastructure.

Peering can be established between VPCs in:
- The **same account and region**
- The **same account but different region** (inter-region peering)
- **Different AWS accounts** (cross-account peering)

## Key Concepts

### No Transitive Peering

This is the most important VPC Peering concept for the exam:

- If VPC-A peers with VPC-B, and VPC-B peers with VPC-C...
- **VPC-A CANNOT communicate with VPC-C** through VPC-B.
- Peering is **only between the two directly connected VPCs**.
- For VPC-A to talk to VPC-C, you must create a **third direct peering** between them.

This limitation is fundamental: VPC Peering is **never transitive** regardless of how many peerings exist in a chain.

### CIDR Restriction

The CIDR blocks of VPCs in a peering **cannot overlap**:

| Scenario | Result |
|---|---|
| VPC-A `10.0.0.0/16` ↔ VPC-B `10.1.0.0/16` | Allowed — distinct CIDRs |
| VPC-A `10.0.0.0/16` ↔ VPC-B `10.0.0.0/24` | Not allowed — overlapping CIDRs |

If CIDRs overlap, the peering connection cannot be created. You must plan the address space before implementing peering at scale.

### Peering Types

| Type | Description | Considerations |
|---|---|---|
| **Same account / same region** | Simplest case. No additional latency between AZs if resources are in the same AZ. | Transfer within the same AZ is free. |
| **Same account / different region** | Inter-region peering. Traffic travels over the AWS backbone. | Data transfer cost between regions. |
| **Different account** | The target VPC owner must accept the request. | Requires the target VPC ARN to identify it. |

### DNS Resolution Across Peering

By default, DNS resolution does not work correctly across a peering. To resolve DNS hostnames of resources in the peer VPC with their private IPs, you must enable:

- **"DNS resolution from accepter VPC"** in the peering configuration.
- **"DNS resolution from requester VPC"** in the peering configuration.

Without this setting, DNS names of resources in the peer VPC will resolve to public IPs instead of private ones.

### Scalability: n*(n-1)/2 Formula

The number of peering connections needed for a full mesh grows quadratically:

| Number of VPCs | Peerings Required |
|---|---|
| 2 | 1 |
| 3 | 3 |
| 4 | 6 |
| 5 | 10 |
| 10 | 45 |
| 20 | 190 |

For more than 5-10 VPCs, the complexity becomes unmanageable. In those cases, **Transit Gateway** is the correct solution.

## Comparison: VPC Peering vs Transit Gateway

| Feature | VPC Peering | Transit Gateway |
|---|---|---|
| **Transitive routing** | No | Yes |
| **Connections needed (5 VPCs)** | 10 peerings | 5 attachments |
| **Cost** | No charge for peering (data only) | Per attachment-hour + data processed |
| **Complexity** | High at scale | Low (centralized hub) |
| **Connection limit** | 50 active per VPC (can request increase) | 5000 attachments per TGW |
| **Multicast** | No | Yes |
| **Use cases** | Few VPCs, simple connectivity | Many VPCs, complex routing |

## Use Cases

| Use Case | Description |
|---|---|
| **Sharing services across teams** | A security team has a VPC with shared tools; other teams connect via peering. |
| **Environment separation** | Production VPC connected to logging or monitoring VPC via peering. |
| **Simple multi-account architecture** | When the number of VPCs is small (2-5) and does not justify the cost of Transit Gateway. |
| **Database service access** | An application VPC accesses a data VPC through peering. |

## Configuration Steps

1. **The Requester VPC:** from the source account/VPC, create the peering request specifying the destination VPC ID (and region/account if cross-region/cross-account).
2. **The Accepter VPC:** the owner of the destination VPC must accept the peering request in the console or via CLI/SDK.
3. **Update requester route tables:** add a route in the route tables of the requester VPC subnets pointing to the peer VPC CIDR, with the peering connection ID (pcx-xxx) as the target.
4. **Update accepter route tables:** likewise, add a route in the route tables of the accepter VPC subnets pointing to the requester VPC CIDR. Both sides are required.
5. **Verify security groups:** ensure the security groups of target resources allow traffic from the source VPC CIDR.
6. **Enable DNS resolution (optional):** if you need private DNS resolution across the peering, enable the DNS options in the peering configuration.

<Callout type="warn">
**Exam Tips — SAA-C03:**

- **No transitive peering:** if VPC-A ↔ VPC-B and VPC-B ↔ VPC-C, VPC-A CANNOT reach VPC-C. You always need a direct peering between every pair of VPCs that need to communicate.
- **CIDRs cannot overlap:** if the scenario has VPCs with overlapping IP ranges, VPC Peering is not possible. Consider PrivateLink in that case.
- **You must update route tables on BOTH sides:** creating the peering is not enough. If you forget to update routes in one of the VPCs, traffic will not flow.
- **Enable DNS resolution for private name resolution:** without enabling this option, DNS will resolve to public IPs instead of private IPs across the peering.
- **VPC Peering does not scale well:** for scenarios with many VPCs, the correct answer is Transit Gateway, not VPC Peering.
- **Peering itself has no cost** — you only pay for data transfer (especially between regions or different AZs).
</Callout>
