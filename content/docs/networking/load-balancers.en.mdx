## Overview

**Elastic Load Balancing (ELB)** automatically distributes incoming traffic across multiple targets (EC2 instances, containers, Lambda functions, IPs) in one or more Availability Zones, improving application availability and scalability.

AWS offers three modern load balancer types: **ALB** (layer 7), **NLB** (layer 4), and **GWLB** (layer 3).

## Key Concepts

### Load Balancer Types

| Feature | ALB | NLB | GWLB |
|---|---|---|---|
| **OSI Layer** | Layer 7 (HTTP/HTTPS) | Layer 4 (TCP/UDP/TLS) | Layer 3 (IP packets) |
| **Use case** | Web apps, microservices, containers | Gaming, real-time, static IP | Third-party security appliances |
| **Static IP** | No | Yes | No |
| **Target types** | IP, instance, Lambda | IP, instance, ALB | IP, instance |
| **GENEVE protocol** | No | No | Yes (port 6081) |
| **SSL termination** | Yes | Yes (TLS passthrough optional) | No |
| **WebSocket** | Yes | Yes | No |
| **Content-based routing** | Yes | No | No |

### Sticky Sessions

Sticky Sessions ensure requests from the same client are always directed to the same target.

| Type | Description | Duration |
|---|---|---|
| **Duration-based** | Cookie generated by the load balancer (`AWSALB`) | Configurable (1 s to 7 days) |
| **Application-based** | Custom cookie generated by the application | Defined by the application |

> **Note:** Sticky Sessions can cause uneven load distribution. Use only when the application requires server-side session state.

### Connection Draining / Deregistration Delay

- When a target is removed or marked unhealthy, the load balancer **waits for in-flight requests to complete** before stopping traffic.
- **Default time:** 300 seconds (5 minutes).
- Configurable range: 1 to 3,600 seconds. Set to 0 to disable.

### ALB Authentication

ALB can authenticate users directly before forwarding the request to the backend:

- **Amazon Cognito:** For authentication with user pools.
- **OIDC compatible:** Google, Facebook, Apple, any OIDC provider.
- The authentication token is passed as a header to the backend.

### Cross-Zone Load Balancing

| Load Balancer | Default state | Inter-AZ cost |
|---|---|---|
| **ALB** | Always enabled | No additional cost |
| **NLB** | Disabled by default | Inter-AZ data transfer charged |
| **GWLB** | Disabled by default | Inter-AZ data transfer charged |

- **Without cross-zone:** Each LB node distributes only among targets in its own AZ.
- **With cross-zone:** Each LB node distributes evenly across all targets in all AZs.

### X-Forwarded-For

- When a client connects through a load balancer, the target sees the load balancer's IP, not the client's.
- The **`X-Forwarded-For`** header contains the original client IP.
- **`X-Forwarded-Proto`** contains the original protocol (HTTP or HTTPS).
- **`X-Forwarded-Port`** contains the original port.

### GWLB (Gateway Load Balancer)

- Designed to deploy, scale, and manage **third-party security appliances** (IDS/IPS, firewalls, packet inspection).
- Uses the **GENEVE protocol on port 6081** to encapsulate traffic.
- Operates at **layer 3**: receives IP packets, sends them to the appliance, and returns processed traffic.
- Typical pattern: inbound traffic → GWLB → appliance (inspection) → GWLB → final destination.

## Comparison: ALB vs NLB vs GWLB

| Feature | ALB | NLB | GWLB |
|---|---|---|---|
| **Layer** | 7 | 4 | 3 |
| **Protocol** | HTTP/HTTPS | TCP/UDP/TLS | IP (GENEVE) |
| **Static IP** | No | Yes | No |
| **Content routing** | Yes | No | No |
| **Lambda as target** | Yes | No | No |
| **ALB as target** | No | Yes | No |
| **Preserves client IP** | X-Forwarded-For header | Yes (source IP) | Yes |
| **Use cases** | Web apps, APIs, microservices | Gaming, VoIP, IoT | IDS/IPS, inline firewalls |

## Use Cases

| Scenario | Recommended Load Balancer |
|---|---|
| Web app with multiple paths (`/api`, `/web`) | ALB with path-based routing |
| Need a static IP for the load balancer | NLB |
| Packet inspection with third-party firewall | GWLB |
| TLS termination at the load balancer | ALB or NLB |
| Route traffic to Lambda functions | ALB |
| Gaming with UDP | NLB |
| Cognito authentication before backend | ALB |

## ALB: Advanced Routing Rules

ALB supports routing rules based on multiple conditions:

| Condition | Example |
|---|---|
| **Path** | `/api/*` → API Target Group |
| **Host header** | `admin.example.com` → Admin Target Group |
| **HTTP header** | `X-Custom-Header: premium` → Premium Target Group |
| **HTTP method** | `POST` on `/upload` → Upload Target Group |
| **Query string** | `?version=2` → V2 Target Group |
| **Source IP** | `10.0.0.0/8` → Internal Target Group |

Rules are evaluated in **priority order** (lower number = higher priority). The last rule is always the default rule.

### Rule Actions

| Action | Description |
|---|---|
| **Forward** | Send to the specified target group |
| **Redirect** | Redirect to another URL (HTTP→HTTPS, domain change) |
| **Fixed Response** | Return a static response (200, 403, 503) |
| **Authenticate** | Authenticate with Cognito/OIDC before forwarding |

## Health Checks

All ELB types perform **health checks** to detect unhealthy targets:

| Parameter | Description | Typical value |
|---|---|---|
| **Protocol** | HTTP, HTTPS, or TCP | HTTP |
| **Path** | Health check endpoint path | `/health` |
| **Healthy threshold** | Successful checks to mark healthy | 3 |
| **Unhealthy threshold** | Failed checks to mark unhealthy | 3 |
| **Timeout** | Wait time for response | 5 s |
| **Interval** | Check frequency | 30 s |
| **Success codes** | HTTP codes indicating health | 200-299 |

> A target is removed from the routing pool if it exceeds the **unhealthy threshold**. It is automatically re-added when it passes health checks.

## Scheme: Internet-facing vs Internal

| Scheme | Description | Use Cases |
|---|---|---|
| **Internet-facing** | ELB has a public IP, accessible from the internet | Frontend, public web apps |
| **Internal** | ELB has only a private IP, accessible only in VPC | Backend, internal microservices, DB layer |

A common multi-tier architecture pattern:

```
Internet → ALB (internet-facing) → EC2 Web Layer
                                         ↓
                              ALB (internal) → EC2 App Layer
                                                     ↓
                                          RDS / ElastiCache
```

## Configuration

Typical steps to create an ALB:

1. Go to **EC2 → Load Balancers → Create Load Balancer → Application Load Balancer**.
2. Select **scheme**: Internet-facing (public) or Internal (private).
3. Select **VPC and subnets** (minimum 2 AZs for high availability).
4. Configure **Security Groups**.
5. Configure **Listeners** (port 80, 443).
6. Create **Target Groups** and add targets (instances, IPs, Lambda).
7. Define **routing rules** in the listener.

<Callout type="warn">
**Exam Tips — SAA-C03:**
- **ALB = layer 7 (HTTP/HTTPS)**, routes by path, host header, query string, source IP.
- **NLB = layer 4 (TCP/UDP)**, faster, supports static IP — choose for gaming or when a fixed IP is required.
- **GWLB = layer 3**, for inline security appliances (IDS/IPS/firewalls) using GENEVE protocol.
- **X-Forwarded-For** to get the real client IP behind an ALB.
- **ALB can route to Lambda functions** as a target.
- **Cross-zone load balancing:** ALB always enabled at no cost; NLB disabled by default, inter-AZ data transfer is charged.
- **Sticky Sessions** can cause uneven distribution — only for stateful applications.
- **Connection Draining** (300 s default) allows in-flight requests to complete before deregistration.
- **NLB preserves the client source IP** natively; ALB uses X-Forwarded-For.
</Callout>
